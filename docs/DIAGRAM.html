1) الطبقات: المشروع بيشتغل إزاي runtime layers

مفيش سيرفر خاص بينا. المتصفح بيكلم Supabase مباشرة عن طريق REST/Auth/Storage.

1الملفات الثابتةindex.html · product.html · barber.html + css/ + js/ + images/تتقدّم من أي استاتيك هوست (أو python -m http.server محليًا)
←
2طبقة الـJSProductStore · SectionsStore · BarberStore · cart · account · admin · sellerكل ملف مسؤول عن جزء، وبيتحمّل بترتيب محدد
←
3Supabase JS v2window.supabaseClient بمفتاح publishable
←
4Supabase BackendAuth (JWT) · Postgres (RLS + Triggers + RPC) · Storage bucket
قاعدة صلاحيات مشروطة: المتصفح ما فيهوش service key. عشان كده أي «مين يقدر يعمل إيه» لازم يتكتب في supabase/*.sql. التعديلات اللي في الـJS لوحدها ما كفايةش — لازم السكربت المقابلها يتنفّذ في SQL Editor.

ترتيب تحميل السكربتات في index.html

supabase-js (CDN) → supabase-client.js → products-data.js → sections-data.js → barbers-data.js
   → barbers-ui.js → sections-ui.js → cart.js → wishlist.js → account.js → admin.js → seller.js → i18n.js → site.js
  • sections-data.js لازم يكون قبل sections-ui.js وaccount/admin/seller (كلهم بيستهلكوا window.SectionsStore).
  • products-data.js بينفّذ initProducts() على DOMContentLoaded، وبعده DoddzSectionsUI بيلزّق كروت الأنشطة في نفس الأقسام (من غير ما يمسح المنتجات) — فلو المنتجات اتعملها re-render، بيتم إعادة اللزق تلقائيًا.
  • بعد أي تعديل JS: زوّد ?v= في كل وسوم <script> في index/product/barber.

3) الأدوار والأقسام who is who

الأدوار (profiles.role)

الدوراللوحةيرى لوحة الأدمن؟
visitor«حسابي»: مشترياتك / عنوانك / تتبع الطلب — وشراء بدون تسجيل أصلاًلأ
seller / merchant / service_providerلوحة البائعلأ
adminلوحة البائع + Product Manager (من «حسابي»)نعم (حصريًا)
role محروس بـtrg_guard_profile_role: المتصفح ما يقدرش يرقية لنفسه. الأدوار بتتعيين من SQL Editor أو من لوحة الأدمن بحساب أدمن. بوابة لوحة البائع الحقيقية بقى profiles.category (يعني الحساب اللي ليه نشاط في جدول قسم) — فالحساب الجديد بيشتغل فورًا من غير ما حد يغيّر دوره.

الأقسام الأربعة = جدول مستقل لكل قسم

القسمصاحب النشاطجدول Supabase
قصهاصاحب صالون حلاقةbarber_profiles
لمعهاصاحب مغسلة سياراتcarwash_profiles
اناملفنّان هند ميدhandmade_profiles
كسبنيتاجر منتجاتmerchant_profiles

الجداول الأربعة نفس الأعمدة بالظبط (superset) + خصوصية لقصها (bio, avatar_url). جدول مراجع service_categories بيربط الكود ← الاسم العربي ← اسم الجدول.

4) تدفق تسجيل صاحب نشاط signup → Supabase → admin

الحساب يشتغل فورًا، والموافقة تتحكم في الظهور للعملاء بس.

1المستخدم يفتح «حسابي»زرار التاجر بيديله شاشة (دخول / طلب انضمام)
←
2يملا النموذج ويختار القسم#ss-type: زائر / كسبني / قصها / لمعها / انامل
←
3auth.signUp()Auth → auth.users + تريجر handle_new_user يعمل صف profiles بدور visitor
←
4SectionsStore.register()rpc('register_provider_section') — الجلسة بتفضل مفتوحة
5aصف النشاط في جدول القسمstatus = pending — الحارس بيفرض user_id = auth.uid()
←
5bprofiles.category / provider_idالدالة SECURITY DEFINER — role ما بيتغيّرش
←
5cصف في signup_requestsفيه category + user_id + provider_id → يظهر في الأدمن
←
6لوحة البائع تفتح على طولتاب «نشاطي» + إضافة منتج (provider_id بيتسجّل مع المنتج)
7الأدمن: تبويب «أنشطة الأقسام»بيقرأ الجداول الأربعة كلها + فلتر قسم/معلق
←
8rpc('set_provider_status')الفحص جوه الدالة: if not public.is_admin() → رفض
←
9status='approved'بيقفل طلب signup_requests ويحدّث approved_at/by
←
10النشاط يظهر للعملاءسياسة RLS: status='approved' or user_id = auth.uid() or is_admin()
لو تأكيد الإيميل مفعّل: signUp() بيرجع بدون جلسة → الـJS بيخزن الطلب في localStorage['doddz_pending_registration_v1'] + صف signup_requests (لو الأعمدة موجودة)، وأول ما المستخدم يسجّل الدخول SectionsStore.completePendingRegistration() بيكمل خطوتَي 4→5 أوتوماتيك.

من غير 05-provider-sections.sql: الأقسام هتفضل فاضية والـJS هيطبع 404 في الكونسول (barber_profiles, carwash_profiles, handmade_profiles, merchant_profiles) ويرجع للكاش المحلي — يعني النظام شغال بس من غير تقسيم حقيقي في Supabase.
  • DISABLE TRIGGER ALL مرفوض (42501) — عطّل بالاسم: alter table products disable trigger trg_xxx;
  • UPDATE products من الـEditor بيرفضه الحارس (auth.uid() فاضي) — عدّل من لوحة الأدمن بحساب role='admin'.
  • لو سطر فشل: كل الملف اتلف → عدّل وابدأ من أول الملف.
